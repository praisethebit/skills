---
name: implement
description: Implement one issue, review it, close it and ship it. With 2 or more issue numbers, each issue gets its own session.
disable-model-invocation: true
argument-hint: NNN [NNN...]
---

Arguments: `$ARGUMENTS`.

Local extension: read `~/.claude/local/implement.md` when it exists, and follow its steps.

With 2 or more issue numbers, do not implement an issue. Follow the local extension for many issues. With no local extension, tell the user to start one session for each issue, each in its own worktree (`claude -w <NNN>`), and stop. When the user later asks for the state, look in `<work folder>/issues/done/` first: `close-issue` moves a closed issue there.

With one number, implement issue $ARGUMENTS. Each step ends on its completion criterion.

Each `AskUserQuestion` call of this skill (a blocker, the recommended issues of step 4.7, a gap) holds 3 parts: the decision, what each option changes for the user, and the recommended option. The question text starts at the decision. It does not tell how the session got to the question. A question for a blocker also keeps the blocked requirement, the exact command or error, what you tried, and each step that the user must do, as the Blockers rule in `~/.claude/workflow.md` asks.

1. **Read.** Find the issue file at `<work folder>/issues/NNN-*.md`. Read it with the `Read` tool, not with `cat` in Bash. Why: the workflow review keeps the full output only of a `Read` call on an issue file, and its Outcome scorer needs all acceptance criteria. State its number, title and exact path. Compare its `model` value (frontmatter key) with your model. If they differ, stop and tell the user to press `s` in `/model` and pick that model. Why: plain `/model <name>` saves the model as the default for new sessions. State the `effort` value of the issue (if it has one) and tell the user to run `/effort <level>`: a session cannot read its own effort. If the issue is not clear enough to implement without a guess, stop and tell the user: the issue goes back to an Opus planning session. The limit between a stop and a ruling is the proof. When 2 readings of a criterion give different results for its proof, the issue is not clear: stop. When the proof passes with each option, and the ticket and the repo docs name none, the choice is a ruling: a decision that you make because the ticket did not make it (a decision that the user made in a grill is not a ruling). Decide it, do not stop to ask, and note it for step 5. Note each ruling that you make in steps 2 to 4 in the same way. Done when you can name the change for each acceptance criterion.
2. **Implement.** Follow the repo's `AGENTS.md`. Before the first edit of a skill, `AGENTS.md` or `CLAUDE.md`, call the `writing-for-agents` skill. Before the first edit of a human doc, call the `humanize` skill. Done when every acceptance criterion is met. For each criterion, name the evidence: a command output, a file, or a screenshot that you read. If you cannot meet or test a criterion (blocker), follow the Blockers rule in `~/.claude/workflow.md`: ask the user with `AskUserQuestion` and do not go on as if it passed. When the issue has `behavior_spec` with one or more files (not `none`, and not missing), read the section `## Behavior spec` of `~/.claude/issue-tracker.md` and write one or 2 entries for each behavior criterion, in the file of its capability among the named files, before step 4 starts. Why: the review of step 4 must see the entry in the diff. With `none` or no key, make no spec edit. Step 5 does not start while a criterion has no evidence and no accepted gap. A step of a called skill that you did not do (for example a step that `writing-for-agents` or `humanize` names) is a blocker, not a ruling: do it, or ask the user with `AskUserQuestion`. Do not run the device check of the repo in this step: step 4 runs it while the review runs. The device check of the repo is the skill that the repo's `AGENTS.md` runs on a device for an issue, for example `device-check`. A criterion that the device check proves gets its evidence in step 4.

   **Escalation.** When one criterion still fails its check after 2 fixes, do item 1. If the assumption is true, or the third fix fails, stop and recommend the next step of this order:
   1. Write in one sentence the assumption that the 2 failed fixes share. Make one observation that has a different result if it is false (a log line, a run on the old code, a read of the real value). If it is false, make one more fix with the new cause. If this fix passes, go on.
   2. Raise the effort one level: `low` → `medium` → `high`. An issue with no `effort` counts as `medium`.
   3. After `sonnet high`, move to `opus medium`, then `opus high`.
   4. After `opus high`, the issue goes back to an Opus planning session. Use no `xhigh` and no Fable.

   The message of the stop holds the assumption and the result of the observation. Before the stop, write the new `model` and `effort` in the issue file. Tell the user to run `/effort`, or to press `s` in `/model` and pick the new model, in the same session and send "continue". The work stays in the checkout. The issue file keeps the level that finished the work, and the close commit holds that file. A blocker (no access, a timeout) follows the Blockers rule, not the escalation.
3. **Check.** Each criterion needs a proof. A proof becomes a guard (a test that stays in the repo and runs after each later change) only when you can name, in one sentence, the failure that the guard catches. That failure meets all 3 conditions:
   1. A user, or a different part of the system, sees it.
   2. A later change can cause it with no other signal (no compile error, no lint error).
   3. The guard tests it through a public interface: a function that other code calls, a CLI, a screen.

   Write no guard for a private function, a value that the test copies from the code, a one-time migration, or text. When a changed behavior gets no guard, state the reason in one sentence. A guard that a criterion names is mandatory. Other rules:
   - Put a guard at the lowest level that shows the failure: a unit test first. Use a browser test or a device test only for a main user path that the repo `AGENTS.md` lists, or for a behavior that only a real browser or device shows (layout, focus, key input, copy and paste, drag and drop, the URL, a permission prompt).
   - Write an edge-case guard only when it comes from a real bug, when the failure loses data, breaks security or damages a host, or when the acceptance criteria name it.
   - For a bug fix, write the failing test first, before the fix.
   - In a repo with no test seam (IaC, docs, CAD, config), the proof is a lint, a validate step, a dry run or a device check.
   - Fix or delete a flaky guard in the same session. Give it no skip and no retry.

   Show that each new guard fails on the old code: run `git stash push -- <the changed code paths>`, run the test, then run `git stash pop`. Do not put the test files or a `<work folder>/...` path in the list: the new guard must stay. Do not run `git stash` with no paths: it also takes the edits of a different session. Run the unit tests that cover the change, if the repo has them. If the repo has browser tests and the change touches the UI or shared test data, run them in one browser. Do not run `pre-commit` here: the commit in `ship` runs all hooks. Done when each criterion has a proof that passes, and each new guard failed on the old code.
4. **Review and device check.** The review runs on Opus at the level `medium`, in the background. The device check of the repo runs at the same time. In this step, replace `<issue file path>` with the exact path from step 1. Before sub-step 1, when the repo has a device check for this issue, run the tests that the repo `AGENTS.md` asks for before a device check, so the test results are not older than the change. Fix a failure now, before the review starts.
   1. Start the review. Call the Agent tool with `model: opus`, `subagent_type: general-purpose` and `run_in_background: true`. Give it this prompt: `Call the Skill tool with code-review and the arguments "medium <issue file path>". If the skill runs in the background, wait for its result. Do not change a file. Do not do the review yourself: if the Skill call fails, return REVIEW FAILED and the exact error. Return the review output verbatim. If the review has no findings, return NO FINDINGS.`

      Why: a forked skill uses the model of its caller, so the Opus agent makes the review run on Opus, also when the session is not on Opus. So the review shows as an agent inside an agent. This is expected.
   2. Do not edit a file of the change while the review or a background device check runs. The review reads the changed files. The device check installs and tests the build of the files at its start. The build outputs and the logs of the device check are not files of the change. Fix a failure only after both results are in.
   3. When the repo `AGENTS.md` asks for a device check for this issue, run it now with the issue path. A device check that waits for a physical action follows the Blockers rule. When the repo has no device check, or the issue needs none, do nothing in this sub-step: the session waits for the review as before.
   4. Wait for the review result. When the result is already in the conversation (for example, it arrived during the device check), continue at once. Otherwise end the turn: the harness sends a notification. When the device check also runs in the background, wait for both results. A review result with no findings, no `(none)` and no `NO FINDINGS` is a blocker.
   5. Sort each finding:
      - In scope: fix it.
      - Out of scope: use the first line that matches.
        1. Its failure case is an item of `## Out of scope` of the issue, or it cannot occur with a file that is in the repo today or with an input that the app accepts from outside the repo (for example a server reply, a file that passes the schema, the input of a user): drop it.
        2. It is an edge case, and its failure loses no data, breaks no security and damages no host: drop it. An edge case is a failure that needs an input, a timing or a sequence that the normal use of the product does not give. In a repo with no app, the product is the set of tools and skills of the repo, and the normal use is the use that its README or its skill describes. A wrong output with none of these 3 results is below the bar.
        3. Its fix is small: fix it in this ticket, and write one line in the `## Answer` with the finding and the fix. A fix is small when it changes only files that the ticket already changes, and `git diff --stat` of the fix alone shows 20 lines or fewer (insertions plus deletions, test lines and doc lines included, so one changed line counts as 2). When a fix grows above 20 lines, undo it and go to line 4. Steps 4.6 and 4.8 apply to this fix. It needs no new review.
        4. Each other finding: name the file or the input and recommend a follow-up issue.
      - All other findings (a style point, a finding on `## Answer`, the open boxes, `status` or `stage`, the wording, size or metadata of the issue): drop it. Give the count of all dropped findings, the drops of out-of-scope lines 1 and 2 included, in one line.
   6. Fix each in-scope finding and each device-check failure. Sort a device-check failure as step 4.5 sorts a finding, but only when the failure is in no criterion of this issue and its cause is outside the issue: then recommend an issue (or drop it and give the count in one line). A failure in a criterion of this issue is never dropped: fix it or follow the Blockers rule. After a fix that changes code, run the tests that the repo `AGENTS.md` asks for before a device check. Then run the device check again only for the criteria that the fix touches. A fix touches a criterion when it changes code that the check of that criterion runs, also when the fix is for a different criterion. Give the device check the issue path and `criteria: <numbers>`, with the position of each top-level item in the acceptance-criteria list, from 1. When the device check of the repo does not accept `criteria:`, run it in full. After the fix of a device-check failure with no code change (for example a test run), run the device check again for that criterion. A fix that touches no criterion of the device check needs no new device check.
   7. Ask the user about the recommended issues with `AskUserQuestion`. Do not call `ship` before the answer arrives, so the new issue files go in the same commit. Write each new follow-up issue with the `add-issue` skill. Pass it the finding in full: the file, the line and the failure case. Say that a review finding is the source. Ask each new-issue question here. Do not ask one in the final message after `ship`.

   8. After the last code change, wait until no device check runs. Then run the full test run that the repo `AGENTS.md` asks for before `ship`. A run with `ONLY=` or a subset does not count. When the repo names none, run the unit tests of step 3.
   9. A fix for a review finding needs no new review. A code fix for a device-check failure needs one new review. Start it as in step 4.1, with one change to the prompt: in place of "Return the review output verbatim." write `Return verbatim only the findings whose file and line are in this list: <each file and line range of the device-check fixes>. Then write one line with the count of the other findings and the file and line of each. If no finding is in the list, return NO FINDINGS and that line.` The arguments of the Skill call stay `medium <issue file path>`. Before the sort of step 4.5, drop each finding of this review that is not on a line of the list, and count these drops, plus the count that the agent gives for the other findings, in the one line of dropped findings. Sort the other findings as in step 4.5. Start no third review. Each in-scope finding of this review becomes a recommended issue: ask about it as in step 4.7.

      Why: each review of the full change can find new points. A new review after each fix then has no end. The review reads the full change, and a rule in its arguments is not reliable, so the agent and the session apply the limit.

   Done when no in-scope finding of the first review is open, the last device check has no fail (a failure of no criterion with a recommended issue does not count), the last code change has a full test run, and each code fix for a device-check failure has its one review.
5. **Close and ship.** Make one commit that holds the work and the closed issue:
   - Write the `## Answer`. It holds one line for each acceptance criterion: the criterion and its proof (the command, the test or the observation, and its result). A criterion with no proof is a gap. List a gap only when the user accepted it in an `AskUserQuestion` answer. A gap with no such answer is a blocker: ask now, before `close-issue`. The Answer says what changed and names the lasting facts in the README, the config, the behavior spec file (for each behavior fact) or a `why:` comment (only for a fact about an external tool that the code cannot show, or about our own design that no test name or doc can hold), as code-format paths (no Markdown link). It holds one line for each new guard: the guard and the failure that it catches. A guard that a criterion names is mandatory. The Answer has a `### Rulings` list as its own subsection: one line for each ruling, with 3 parts: what you decided, why, and the cost if the decision is wrong. With no ruling, write "None." Then run `~/.claude/bin/close-issue NNN`. Do not read the tracker doc for this step.
   - Call `ship` one time with all changed paths, the issue files included. Include each `edited:` path that `close-issue` prints.
   - Put every issue file that you created or edited in this session in the same `ship` call.

   Use two commits only when a live check needs the push first (for example a deploy that pulls from git): ship the work, do the live check, then close the issue and ship the close.

   If the live check needs a test commit (a forced failure or a removed resource), ship the revert and the close in one commit.

   The final message is the chat message after the last `ship` call (the one that ships the close). It holds these 5 parts and no other part:
   1. The result: the issue is closed and shipped, in one line. The line holds the number and the title of the issue. The title is the text of the `# ` line of the issue file. When the push of `ship` failed, the line says that the commit is not pushed.
   2. The change: 1 or 2 sentences on what is different in daily use for the user. It says what the user now sees, gets, or does not do anymore. It names no file path, no commit hash and no count. It can name a command or a skill that the user types. When the change has no effect in daily use (for example a removal, a refactor or a test), the part says that daily use does not change, and names in one sentence what the change protects or prepares.
   3. Each thing that needs the user: each accepted gap, each new follow-up issue with its number, and each decision that waits for the user. A new-issue question is not a waiting decision: step 4.7 asks it before `ship`.
   4. Each ruling with a real cost: one line with what you decided and the cost if the decision is wrong. A ruling has a real cost when a wrong decision changes the result for the user, or when its undo needs work. A ruling with "Cost if wrong: none" has no real cost.
   5. The next action: the one thing that the user does next, for example "run `/clear` before the next issue".

   Write the final message in this shape:

   ```
   Issue NNN (<title of the issue>) is closed and shipped.
   - Changed: <1 or 2 sentences of part 2>
   - Needs you: <each item of part 3, or "nothing">
   - Rulings with a real cost: <one line for each, or "none">
   - Next: <the one next action>
   ```

   When you are not sure that an item needs the user (part 3) or that a ruling has a real cost (part 4), the item stays in the message. These parts stay out of the final message, and the `## Answer` holds each of them that exists before `ship`: the commit hashes, the state of the push, the list of the tests, the count of the review findings, the counts of the change (files, lines, items), the detail of the change (each changed file and each step of the work, not the `Changed:` line) and each ruling with no real cost. The `## Answer` keeps each ruling with its 3 parts.

   This content list applies only to the final message. A message that stops the session before that `ship` call (a blocker, an escalation, a stop for a different model, an issue that is not clear) keeps its full content.
